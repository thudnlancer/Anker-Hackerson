# 从 HA 决策看板到家庭能源管家

2026-10-14。基于预赛方案、本仓库实际接口和欧洲家庭能源使用场景完成第一版前端重构。改版位于共同仓库 `Anker-Hackerson/explainability-app/frontend`；上层目录中的旧独立 `explainability-app` 副本没有同步修改。

本次完成可运行的六个页面和计划评估交互。现有记录、解释、反事实计算与执行核验沿用后端。新增计划与偏好在浏览器按家庭保存，尚未接入家庭 MILP 或 HA 控制。默认使用英语、德国时区和欧元，支持中文以及德国、荷兰、法国的时区配置。英语首页说明使用记录中的数值事实；原始中文解释和完整证据保留在证据工作台，尚未实现英语或德语服务端解释。

## 1. 用户视角：先让生活按时完成，再解释能源安排

预赛方案明确面向缺少电力知识、没有时间持续看盘的家庭，强调生活目标、选择权、少打扰、现有设备价值和可核验的结果。原前端以三个站点、求解状态、采集时钟、模型版本和控制证据为入口。这对研发有用，但把理解调度系统的负担放到了家庭用户身上。

家庭首页应该帮助用户很快回答三个问题：家里是否需要关注；重要用电安排能否满足；下一步有没有需要自己处理的事。详细原因、对照计算和执行记录在用户需要时展开。

以下家庭类型是设计假设，并非已经开展用户访谈后的结论。默认先覆盖德国的光伏与储能家庭；不假设所有欧洲家庭拥有相同合同、设备或并网条件。

| 家庭场景 | 用户关心的问题 | 产品应提供的判断 |
| --- | --- | --- |
| 屋顶光伏、储能、动态电价 | 晚间电够不够，是否要先买电 | 联合考虑预测、需求、充放电限制和购售电价；解释时间跨度 |
| 阳台光伏与小容量电池 | 白天存下的电晚上能不能用 | 按实际容量、接入电表和出力边界呈现能力，不套用比赛 14 kWh/5 kW 到真实产品 |
| 固定电价或分时合同 | 什么时候安排家电更合适 | 固定价侧重光伏与需求匹配；分时合同遵循合同窗口；不能硬套动态价格套利 |
| 有电动车的家庭 | 能否在出发前完成充电 | 先核对需求、效率、功率、可用窗口，再讨论成本；重要需求优先于等待更低价格 |
| 在意停电保障的家庭 | 停电时哪些设备能用 | 区分全屋备电、专用离网插座和不支持离网供电；电池电量不是备电能力证明 |
| 不愿频繁操作的家庭 | 什么时候真的需要我介入 | 正常时少打扰；需求受影响、状态过期或执行失败时提供具体选择 |

欧盟官方介绍了固定、分时、动态等合同的差异，也指出账单包含能源、网络及税费。基于这些事实，本次将合同类型、购电与外送价格分离、税费口径核对放入家庭设置和费用解释，而不把现货价格直接当成到户账单。[欧盟：电力合同选择](https://energy.ec.europa.eu/news/focus-making-best-choice-your-electricity-contract-2026-03-17_en)

Anker 官方资料已有自用、按电价安排充放电及不同备电模式。我们的产品差异应落在需求兑现、可解释取舍和偏差复盘；单纯增加“AI 模式”按钮不足以解释价值。产品资料用于理解使用场景，比赛设备能力仍以 SOP 和实际接口为准。[Anker Solarbank 3 用户手册](https://support.ankersolix.com/de/s/article/Anker-SOLIX-Solarbank-3-E2700-Pro-Benutzerhandbuch-A17C5)

## 2. 页面如何对应用户任务

| 页面 | 用户任务 | 本次已实现的交互 | 设计原因 |
| --- | --- | --- | --- |
| 家庭首页 Today | 看懂当前情况与下一步 | 单家庭切换、快照时间、数据状态、当前建议、连接示意、备用偏好、电价、计划入口 | 降低初次理解负担；家庭用户不用从三站技术总览开始 |
| 生活计划 Your plans | 把生活需求变成用电安排 | 新建、填写、评估、确认、本地保存、移除；标记快照变化；阻止独立建议时间重叠 | 从出行和家务出发，让时间与需求先于调度参数 |
| 光伏与储能 Solar & storage | 理解现有设备是否用得合适 | 光伏与负载读数、存电、容量空间、窗口预测富余；缺数据时说明缺什么 | 帮助用户判断瓶颈，而非只看 SOC；避免把预测富余当弃光 |
| 能源费用 Energy costs | 看懂估计与最终费用 | 模型费用分解、期末估值、结算状态、购电/外送价格切换、时段查看、证据入口 | 建立账单理解能力，避免把负模型目标包装成真实盈利 |
| 家庭偏好 Home preferences | 按家庭条件安排自动化 | 优先目标、备用偏好、合同、安装、申报备电能力、地区设置；按家庭保存 | 用户表达目标，后续系统负责转为经过验证的模型参数 |
| 决策证据 Decision evidence | 深入了解和核验 | 保留三站总览、详情、提问、实际模型反事实、回读、结算和来源；可直接打开决策 | 原有能力继续可用，把技术细节放到用户主动探索的一层 |

首页不给出无证据的“今日省了 €X”“全屋可续航 X 小时”“日自用率”。需要实际购售电、电池遥测、日累计计量、匹配基线或备电负载时，直接显示待补充的数据。Home Assistant 的官方能源文档同样区分瞬时功率与累计电量；本次沿用此边界。[Home Assistant 能源管理](https://www.home-assistant.io/docs/energy/)

桌面使用侧栏、主任务与次级证据入口；手机使用底部五项导航，详细证据由首页原因链接进入。界面采用浅色底、暖白内容区、低饱和绿色和简洁连接示意。需要关注的事项使用琥珀色，预测与建议不使用已完成标识。触控操作提供至少 44 px 的主要按钮，数字旁保留单位；提供键盘焦点、跳转内容、原生模态框和减少动画支持。

## 3. 计划交互与算法边界

### 3.1 从需求到确认

1. 选择电动车、洗碗、洗衣或其他用电任务。
2. 录入需求电量、设备功率、最早开始与最迟完成。电动车需申报充电效率。
3. 先检查输入、预测覆盖范围和所需输入电量；超出能力时提供延长时间、减少需求或核对更高可用功率的选择。
4. 可暂停任务在窗口内按购电价选择时段；连续任务选择一段连续时间，保持相同恒功率近似。
5. 展示建议时段、输入电量和预计购电成本。用户明确确认后才保存建议。
6. 保存记录包含家庭、原决策 ID、设备时刻、需求、评估结果及保存墙钟。后续决策 ID 改变时提示重新评估。

演示时间来自 `device_time + index × step_hours`，按 IANA 欧洲时区显示。下拉框携带时段索引，对应真实 UTC 瞬时；夏令时回拨时，同名本地小时可通过 CEST/CET 区分，不把 macOS 的香港时区当成德国家庭时间。窗口长度以记录中的有效预测为准，四步演示不会伪装成已具备 24 小时预测。

### 3.2 本次能够证明什么

- 时间与功率判断：所需输入电量 = 需求电量 ÷ 申报效率；窗口可提供电量 = 申报功率 × 时长。
- 建议成本：按每个选中时段的输入电量乘以记录中的购电价累加。
- 最后一个时段允许部分电量，保留精确电量收支；选择同价时段时优先更早的时段。
- 洗衣、洗碗禁止可暂停选项，以恒定功率近似生成连续窗口。
- 已保存的独立建议有重叠时阻止再次确认，要求调整窗口或移除旧建议。
- 负外送价允许展示；本项目官方语义不支持负价购电补贴，因此遇到负购电价时拒绝计划估算并要求核查。

这是独立的时间/功率检查与购电价格建议。它没有联合优化家庭基载、电池、光伏、热泵舒适度、并网容量和多个设备，也没有实测家电功率曲线。不能把“时间与设备功率可以满足”解读为家庭端已经具备全部执行条件，更不能将该费用当成家庭总账单差额。

原有反事实仍在证据页通过 API 创建持久任务，由独立 worker 用对应模型重算；它与本地计划建议是两种不同用途的计算。后者没有使用 MILP 名称，也没有替代原模型。

### 3.3 用户偏好如何进入未来的真实调度

当前偏好只在浏览器保存，备用线也是草案提示。接入后，必须先将目标转换为结构化约束与成本预算，显示前后预计影响，再经用户确认进入重新优化。备用需求作为模型内部目标；不改写 SOP 锁定的设备 SOC 配置。已有 HA 控制语义、写保护、状态校验、指令提交及回读链路应继续复用。

## 4. 新功能开发建议与原因

| 优先级 | 功能 | 欧洲家庭的价值 | 所需接入与验收 |
| --- | --- | --- | --- |
| P0 | 家庭能力档案与电价合同接入 | 让建议适配固定、分时、动态合同及实际安装，避免推荐不存在的能力 | 购售电价分别保存、税费/服务费/发布时间、地区时区、进出口上限、容量、充放电能力、离网拓扑；按实际合同重算费用 |
| P0 | 生活计划服务与联合可行性检查 | “明早车要能用”比“优化目标是什么”更容易表达 | 后端持久化与版本、需求窗口、功率/效率、控制授权、家庭容量；分清已在基载中的需求，避免重复计入；多计划联合优化 |
| P0 | 重要需求与异常处置卡 | 天气变化或数据断流时，知道计划受什么影响、要不要操作 | 将需求、预测版本、执行、设备回读关联；状态过期时不显示无条件安心；每条告警提供恢复路径与去重机制 |
| P1 | 计划兑现与费用偏差复盘 | 用户能核对系统是否守住出发时间和家庭偏好 | 计划→候选→过滤→提交→回读→结算统一关联；保留同初始状态、同能力、同信息的对照，区分预测差与实收差 |
| P1 | 手动接管与自动恢复 | 临时改行程时，能更改目标并知道何时恢复自动化 | 生成目标草案、核对代价、确认、策略版本、过期时间、撤销与回读；不做直接聊天写功率 |
| P1 | 光伏消纳机会卡 | 阳光好的午间，把可调整家务变成具体选择 | 日累计能量、实际电池/电网功率、真实可调整负载、实际安装上限；只有具备潜在出力与限发记录才核算弃光 |
| P1 | 英语/德语解释与通知偏好 | 更贴近家庭语言，减少长期使用负担 | 事实模板本地化、术语与单位一致；正常运行只做摘要，需求风险才通知；用户确认后才启用消息发送 |
| P2 | 热泵舒适度与 EV 联动 | 兼顾冬季舒适和出行，扩大可调整负载 | 温度/室内舒适边界、车辆在家状态、实际充电接口、家电测量与回读；避免直接把热泵当可任意移位的 kWh |
| P2 | 电池使用与容量适配复盘 | 判断现有设备够不够，而不是只看一个累计节省数字 | 长周期吞吐、循环代理、容量和需求缺口；结合基线、天气与合同变化评估，不承诺生命周期 ROI |

开发顺序建议：先完成真实合同与设备档案，再让用户计划进入后端及调度，随后做需求异常与结果复盘。真实状态、原始账单口径和计划执行必须先打通，才能对外提供实际节省金额和自动化兑现承诺。

## 6. 本地运行与验收

前端构建：

```bash
cd Anker-Hackerson/explainability-app/frontend
npm test
npm run build
```

按 [运行说明](operations.md) 启动 API 与 worker；前端生产包由后端同源提供，新增功能不需要新增 npm 依赖。本轮预览地址为 `http://127.0.0.1:8086`，使用 `artifacts/ux-redesign/demo.sqlite` 独立人工演示库。它不是线上 HA 页面发布，也不是实际设备闭环验收。

验收记录和界面截图见 [本轮验收](ux-redesign-acceptance.md)。

## 7. 后续用户验证

在德国屋顶储能、阳台光伏和不同合同的家庭中分别做任务测试。让用户在无指导条件下完成“判断是否需要关注”“添加明早用电需求”“解释一个预计费用”“查找建议与实际执行的区别”。记录首次判断正确率、完成时间、错误操作和用户能否说清费用与备电边界。

首轮成功标准建议：用户无需打开技术证据即可判断下一步；不会把预测当收入、建议当执行、备用偏好当硬件保障；需求不可行时能选出一种有效调整。尚未开展这类用户测试，本次视觉和软件验收不能代替用户研究。
