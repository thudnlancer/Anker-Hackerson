# 光伏储能策略系统架构 Guideline

> 当前架构基线；在线流程验收状态见 [在线流程里程碑](../milestones/ONLINE_FLOW_MILESTONE.md)。

## 1. 基线结论

系统的核心是一个具备跨站点泛化能力的滚动充放电策略，而不是一个必须依赖长历史数据才能启动的站点预测模型。

系统输入的优先级固定为：

1. 比赛 API 返回的今日/明日电价与天气；
2. HA 返回的当前设备状态、光伏功率、负载功率和 SOC；
3. 基于 HA 历史建立的在线校准参数和辅助预测；
4. 安全回退策略。

API 在每次重规划时重新读取。不能把首次获取的今日/明日数据视为全天不变；如果 API 响应动态变化，应以最新、时间戳有效且字段完整的响应为准。

SOP 口径补充：设备时间由模拟器加速，策略只用 HA 的 `device_time` 或价格 API 的当前档位判断“现在”；本机/HA 服务器墙钟只用于维持约 5 秒真实时间轮询和检查 HTTP/HA 传输新鲜度。价格按小时分档，天气按站点提供今日/明日逐小时数据；买电价为正，卖电价可能为负，负卖电价表示向电网送电会产生损失，不是买电补贴。

正式比赛和模拟比赛的结算窗口都是 168 个设备小时（7 天）；模拟赛可以反复启动，正式赛在每个纪元只能启动一次。策略可以使用 24 小时滚动优化视域，但这不是比赛窗口长度，也不能把 24 小时设计参数写成 SOP 规定。

比赛窗口启动后（准备倒计时期间即可），`/api/contest/history?site=N` 可提供该站点窗口前 7 天的逐小时真实观测；窗口尚未启动时返回 404 只表示当前没有可用窗口。每个点必须带 `time`，响应声明 `interval_hours=1`，字段与训练集同口径（光伏、负载、天气观测和 `is_day`，共 29 列口径）。该历史是无扰动的真实观测，可用于辅助预测、PV 校准和 warm-start，但不包含当前 SOC、电池充放电、并网功率或控制状态；实时设备状态仍必须从 HA 读取。

API 看板令牌和 HA 长期令牌是两套独立凭证：价格、天气、比赛历史走看板 API 认证，设备状态和控制只走 HA REST API。令牌不得写入训练产物、快照或提交仓库。

## 2. 分层架构

```text
价格 API：今日/明日价格 ─────────────┐
天气 API：今日/明日天气、辐照度 ───────┤
                                      v
HA：PV、负载、SOC、电池功率、并网功率 ─> 数据契约与时间对齐
                                      |
                                      v
                         在线电网-电池-负载物理模型
                         ├─ PV-辐照度校准
                         ├─ 负载短期预测/区间
                         ├─ 充放电效率与待机损耗
                         └─ SOC、功率和能量平衡校准
                                      |
                                      v
                     SOP 约束滚动 LP/MILP 策略
                     ├─ 24 小时滚动视域（可配置，不是比赛窗口）
                     ├─ 15 分钟候选步长（需按实际 API/设备粒度展开）
                     ├─ 按设备 tick 重规划，不能假定固定 5 分钟设备步长
                     └─ 只执行计划第一步
                                      |
                                      v
              电池功率 -> 并网点指令映射 -> 下发 -> 下一 tick 回读
                                      |
                                      v
                           结果审计与安全回退
```

### 2.1 数据接入层

每次循环保存一份带来源和时间戳的快照，至少包括：

- 价格：`start`、`end`、购电价、售电价；
- 天气：时间戳、温度、云量、辐照度、天气状态；
- HA：`device_time`、`solar_power`、`home_load`、`soc`、充电功率、放电功率、并网进/出功率、设备模式；
- 请求接收时间、API 响应版本或哈希。

所有跨日数据按完整时间戳对齐。价格必须合并 today/tomorrow 的完整时间戳窗口，禁止按单日数组索引跨日回绕；天气按站点隔离，不能把站点 1 的预测复制给其他站点。

`contest/history` 的接入必须先通过严格校验再进入模型：`site` 必须为 1/2/3；历史点按 `time` 升序且不得重复；相邻点必须连续 1 小时；`interval_hours` 必须为 1；字段缺失、单位不明、时间不连续或响应站点不匹配时整批拒绝，不以 0 填充。缓存记录获取时间、窗口起止时间、站点和字段哈希，不记录任何令牌；同一窗口可复用缓存，但不能用旧窗口覆盖当前 API/HA 数据。

API/HA 数据的新鲜度和设备时间必须分开判断：墙钟只用于请求超时、约 5 秒真实时间轮询和传输新鲜度；策略当前小时、价格档位、昼夜状态和历史对齐只认 `device_time` 或带时区的 API 时间戳。无法从两者建立一致设备时间坐标时，阻断经济动作并保留诊断快照。

缺少明日价格窗口、当前 HA 状态过期或 API 时间戳无法对齐时，不生成经济动作；可以继续只读采集和安全回退，但不得假造功率、价格或时间。`contest/history` 是辅助输入，历史响应未通过校验时应丢弃该历史并继续使用有效的 API/HA 当前数据，不能把历史接口失败误当成策略启动硬门槛。

### 2.2 在线物理模型

基本功率平衡为：

```text
电网净输入 = 负载 - 光伏 + 电池充电 - 电池对负载/并网的放电
```

这里的 `电池放电` 是物理模型中的电池侧功率；HA 第三方控制的 `discharge` 设定值不是该功率，而是并网点输出（外送）目标。电池实际放电量必须由目标、光伏余量和负载实时反解；光伏余量已经满足目标时，设备可能不放电。`charge` 的设定值才直接表示电池充电功率。

SOC 递推应使用实际 tick 时长和实测效率：

```text
E_next = E + eta_charge * P_charge * dt
          - P_discharge * dt / eta_discharge
```

模型应持续估计或校准：

- 辐照度到实际 PV 的转换关系；
- 充电效率、放电效率和待机功耗；
- 电网/光伏/负载/电池功率平衡残差；
- SOC 读数偏差；
- 负载的短期波动范围。

按 SOP，默认能量损耗只在充电侧计入约 0.95 效率，放电侧不再重复扣除效率；若现场回读证明存在额外损耗，才作为实测参数覆盖默认值。

损耗不能重复计价：效率损失由 SOC/能量模型体现，寿命损耗由吞吐成本体现，负外送电价由外送结算体现，测量误差只进入诊断和安全裕度。

### 2.3 辅助预测层

- 如果 API 直接提供未来 PV/负载，直接使用 API 数据；
- 如果只提供天气，则由辐照度和 HA 校准关系估计未来 PV；
- 未来负载没有确定性 API 时，使用当前负载、短期历史和保守区间；
- 预测结果永远不能覆盖有效 API 数据；
- 预测失败时使用安全回退，不阻塞状态读取和风险控制。

`lag_168` 和“连续 168 小时历史”只属于旧的递归预测实现，不是主策略的启动条件。历史数据可用于提高负载预测和物理参数校准，但不应阻塞 API 驱动策略。

### 线上历史缓存生命周期

线上辅助预测与历史采集必须并行运行，不能把一次 `ready=true` 检查误当成
永久资格。`ready=true` 只说明检查时缓存末尾存在连续 168 个设备小时；在
加速比赛中，停止采集后设备时钟继续前进，缓存尾部会立刻变旧，不能再直接
用于当前 API 天气窗口的预测。

线上循环应按以下顺序执行：读取当前 HA 状态和 API 天气，按站点校验并追加
当前观测，检查该站最新 168 小时是否连续且尾部与当前 `device_time` 相接，
然后才允许辅助模型预测。采集器不能在模型运行期间停止；若采集失败、尾部
断档或与当前设备时间脱节，单站模型标记为 `model_unready`，策略仍回退到
API-first 的当前 PV/负载持久化或保守区间路径。不得用墙钟时间、0 填充或
伪造天气点来跨越断档。

门禁分为质量层而不是策略总开关：最新连续 168 小时为 `full_168h`，连续
至少 24 小时但不足 168 小时为 `degraded_minimum`，低于 24 小时才标记
`unready`。只有当前设备时间不新鲜、API 关键窗口缺失或状态无法校验时，
才阻断该站经济动作；预测模型暂时不可用本身不能阻断 API-first 策略输出。
短暂采集故障造成的尾部滞后可在有限容忍窗口内标记为 degraded forecast；
超过容忍窗口则关闭辅助模型并回退持久化输入。容忍窗口不能跨越长期断档，
也不能把旧预测直接当作当前设备状态。

冻结缓存只用于可复现实验、回放和模型审计，必须与 `live_history` 目录分离。
比赛运行时应保留一个持续更新的 live cache；`contest/history` 在窗口启动后
可作为严格校验的 warm-start，但不能替代当前 HA 状态，也不能让停止采集后
仍声称线上历史与当前设备时间连续。

### 2.4 策略层

策略输入为当前 SOC、当前 PV/负载、API 价格/天气窗口、物理参数和设备指令边界。目标至少包含：

- 购电成本；
- 外送结算收益或负外送损失；
- 电池吞吐/寿命代理成本；
- 期末 SOC 价值或安全储备；
- 必要的功率平衡和设备损耗约束。

优化器必须直接使用 SOP 可表达的并网点约束。不能先产生无法映射的电池功率，再在下发前静默截断。

离线 replay 应在计划阶段将电池侧 `discharge_w` 按计划 PV/负载转换为非负并网点目标并验证目标范围；执行阶段保持该目标，再依据实际 PV/负载反解电池侧功率，不能用实际值重新生成另一条指令或静默截断。正式 live 前应将并网点目标直接建模为优化变量，或在计划阶段对预测误差加入可表达性/安全裕度约束。

### 2.5 执行层

每轮只执行计划第一步：

1. 验证当前状态新鲜度；
2. 将电池动作转换为并网点目标；
3. 检查功率范围和动作可表达性；
4. 下发后等待下一设备 tick；
5. 核对设备模式、方向、设定值、电池功率和并网功率；
6. 回读失败则停止该站点新动作并进入安全策略。

执行边界必须遵守 SOP：设备状态读取和控制写入都经 HA 实体/服务完成，禁止策略直连 Modbus 端口。切换 `operating_mode` 后等待约 1 秒再发送方向和功率；`charge` 的功率值是电池充电功率，`discharge` 的功率值是并网点输出目标。策略内部的 `hold` 必须表示保持当前安全状态，不能静默映射成零充电或任意切换到自发自用。

时间加速下，官方示例倍率 `x180` 时一个 5 秒真实 tick 约对应 15 分钟设备时间，一个设备小时约 20 秒真实时间。5 秒是轮询/控制反馈节奏，不等于设备拥有 5 秒粒度的观测；“5 分钟重规划”只能作为待验证的聚合设计，不能覆盖实际 tick，也不能使用墙钟每小时定时。每轮应重新读取 `device_time`，只执行当前计划的第一步，并在下一 tick 回读确认。

比赛将 SOC 可用范围固定为 0%~100%；优化器的内部安全储备、保守下限或回退阈值必须作为独立策略参数记录，不能冒充比赛规则。默认损耗约 5% 只计入充电侧，放电侧不重复扣减。

## 3. 训练集和实验口径

`forecast_data/` 的 100 个站点、每站 2,208 个小时点用于：

- 统一策略在多站点上的离线 replay；
- 物理约束、成本、SOC 和安全边界验证；
- 参数敏感性和跨站点泛化统计。

它不是当前三台比赛设备的历史替代品，也不用于训练站点特定策略。若使用预测器，必须把预测器训练和策略泛化评估分开报告，不能把预测模型指标直接当成策略收益。

比赛评分不是单纯的运行期成本：排名使用三站合并的 `saving_settled_percent = ΣΔR_settled / ΣK`。`ΔR_settled` 还包含窗口结束时电池库存按整场平均买电价计算的结算价值；`saving_percent` 仅是已实现收益参考值。优化器的期末库存价值因此应使用 API/窗口口径估计的平均买电价，不能固定写成任意常数并当作官方结算价。

2026-10-13 消融复核补充：必须分别报告运行期电费、期末库存价值、结算改善和内部寿命成本。库存收益是有效比赛收益，不因其占比高就予以排除；人工吞吐损耗系数也不能当作官方扣分项。滚动 24 小时视域的末端估值与真实 168 小时比赛结束的结算价是两种用途，优化时只能使用当时已公开信息估计，评估时才可使用整场平均购电价。候选策略之间的成本差不能直接称为官方得分，仍需与自发自用基线比较并计算 K 分母。

20 站四臂回放支持优先验证 API 辐照度校准 PV，而非无条件接入旧共享模型。负载模型单独使用的运行期收益较弱，但与 PV 模型组合仍有小幅增益，因此暂不删除该辅助候选；下一步应比较当前负载、负载区间与辅助预测的多场景策略表现。详见 `NEXT_STAGE_RESULTS.md` 的四臂消融章节；该结论不改变 API-first 优先级，也不将历史长度提升为主策略启动门槛。

离线 replay 必须区分：

- API 在决策时已可获得的价格/天气；
- 当前 HA 可获得的 PV/负载/SOC；
- 未来真实值仅用于事后误差评估，不得泄漏到决策输入。

## 5. 下一阶段实现顺序

1. 建立 API 快照、HA 状态和请求版本的统一数据契约；
2. 实现 `contest/history` 的响应校验、按窗口缓存和字段哈希审计；历史仅用于辅助预测、PV 校准和 warm-start；
3. 从 HA 实时数据估计电网-电池-负载模型和 PV 校准参数；
4. 在 100 站点数据上运行不训练站点策略的 API-style replay，严格模拟“决策时可见”数据；
5. 加入动态 API 变化、缺失、延迟、跨日和负载突变测试；
6. 将 API 驱动策略接入 shadow-run（已完成只读接入，需继续验证动态快照）；
7. 完成单站受控写入、等待真实 tick 并回读模式/方向/功率/SOC/并网功率；
8. 单站验收后才扩展三站 live；先反复运行模拟赛，正式比赛在队名、纪元闸门和策略健康检查均确认后只能启动一次。

本 guideline 确认前，不删除旧结果，不冻结比赛参数，也不把任何离线收益声明为官方成绩。

## 7. 显式空闲指令与真实 API 校准试验（2026-10-13）

成功优化计划的 idle 与失败回退必须区分：离线 `hold_mode=zero_flow` 把
计划中的零电池流量表示为待验证的 `charge=0 W`，不能误写为 `discharge=0 W`。
自发自用 baseline 和失败回退固定为 self_consumption，不能随诊断开关改变。
默认 HA 客户端及在线策略未更改；zero-charge 在只读 shadow 中必须显式标记
硬件未验证、未下发。已验证数学模型与该零流量模拟的 SOC、并网及目标值一致，
但不意味着真实硬件闭环完成验收。

真实 API/HA 只读配对已接通，完整快照另存，旧缓存不得补造辐照度。新增采集
字段不会自动更新仍运行的旧进程。校准只使用更早设备时间与接收时间的配对，
按小时聚合避免频繁 tick 过度加权；日照历史不足继续产生持久化候选。

首次 24 轮日间试采的冻结 1/2/4 小时预报表明：少量日照小时得到的中位比例
不够稳健，站点 1、3 的 1 小时预测比当前 PV 持久化更差，4 小时有改善。
不得将“3 个日照小时可拟合”当成上线门槛，或以单日小样本认定分时距切换阈值。
下一阶段验证短期实测锚定、API 辐照度驱动的较远期 PV 及有界偏差修正，
始终保留可用回退；这不是降低 API 优先级，而是校验站点物理转换关系。

当前冻结预报小样本的收缩诊断显示：1 小时偏向 persistence，4 小时偏向
辐照度校准，2 小时差异很小。因此不能把 API 辐照度或一个固定混合权重无条件
接管所有提前量；应按时距和不确定性门槛选择，并在收益层验证后才改变动作。

试采只证明数据、候选策略和冻结预报评估流程可运行；无 HA 控制写入、无
真实调度收益验证。结果与产物位置见 NEXT_STAGE_RESULTS.md 最新两节。
